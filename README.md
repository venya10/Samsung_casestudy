# Samsung MENA — Marketing Intelligence

Case study submission. A weekly marketing intelligence system: one source extract
in, a cleaned analytical model, an efficiency and benchmarking analysis, an
early-warning rules engine, a branded executive dashboard, and an AI assistant that
answers questions by querying the data rather than guessing at it.

**All figures AED · 8 weeks · 8 subsidiaries · 8 channels · 6 devices**

---

## Quick start

```bash
python -m venv .venv
.venv\Scripts\activate                # Windows;  source .venv/bin/activate elsewhere
pip install -r requirements.txt

python src/run_all.py                 # full pipeline, ~3 seconds
start site\index.html                 # the dashboard — 8 pages, click-to-filter, opens offline
```

For the live AI assistant (otherwise it runs prepared answers and says so on screen):

```bash
copy .env.example .env                # then add your key, or:
set GEMINI_API_KEY=...                # free key: https://aistudio.google.com/apikey
python src/serve.py                   # then open http://localhost:8000
```

## The three decisions that shaped this

**1. There is no marketing mix model, deliberately.**
Eight weeks cannot identify advertising carryover — estimating a decay rate needs
the response to a spend change observed over many cycles. A mix model here would
produce confident channel ROIs that are not recoverable from the evidence.
Reporting them would be the most criticisable thing in the analysis, so they are not
reported. What 64 market-weeks *do* support is measured efficiency, cross-market
benchmarking, and an association model with its uncertainty left visible.

**2. TV is excluded from every ranking rather than scored as zero.**
TV carries 48% of media spend and no attributed sales. That is a measurement gap,
not a performance result — and the two must not be allowed to look alike. The panel
model separately finds TV spend positively associated with sales, which is the
argument for *measuring* it rather than cutting it.

**3. The early-warning system compares markets, not weeks.**
A conventional system watches a metric against its own trailing history. With 8
weeks that baseline does not exist. This data instead has a panel of 8 comparable
subsidiaries, so the primary detector asks *is this market unlike its peers this
week?* — available from week 1 rather than needing a quarter to warm up.

## How it fits together

```
data/raw/samsung_marketing_full_dataset.csv
      │  ingest.py     verify structural sparsity, establish brand-metric grain,
      ▼                drop the duplicate column, log every judgement
   cleaned long table  ──▶ data_quality_log
      │  model.py      reshape to facts + dims; week × market is the spine
      ▼
data/processed/*.parquet  +  marketing.duckdb
      │
      ├── insights.py       efficiency · market scorecard · product×channel ·
      │                     panel model with CIs
      ├── alerts.py         rules engine over config/rules.yaml
      ├── build_site.py     the static dashboard
      └── assistant.py      Gemini + read-only SQL tools
```

**One definition per KPI, in one place.** `model.py` computes them, the site reads
them, and the assistant gets the same definitions in its system prompt. A number
cannot disagree between the dashboard and the assistant's answers.

## The dashboard

A static HTML site ([`site/`](site/), generated by
[`src/build_site.py`](src/build_site.py)) is the one dashboard. Eight pages —
Overview, Channels, Portfolio, Influencers, Brand & Share, Early Warning, Data, AI
Assistant — hand-rolled inline-SVG charts, no charting library and no web
framework: self-contained, opens offline by double-clicking `site/index.html`,
weighs kilobytes.

It still cross-filters: [`assets/app_filter.js`](assets/app_filter.js) reads a
filter bar and any chart element carrying `data-fdim`/`data-fval`, re-fetches the
filtered tables, and re-runs every chart on the page against that slice —
including the underlying analysis (ROI, market scorecards, reallocation), not
just which bars are highlighted. `src/serve.py` uses the standard library's
`http.server` to serve the filtered-table API and the AI assistant's two routes;
without it, `site/index.html` still opens and renders directly from disk, just
without live filtering or a live assistant.

Colour is validated, not chosen by eye:

- **Samsung Blue `#1428A0` is brand chrome, not a data colour.** At OKLCH L=0.364 it
  sits below the categorical lightness band and would fail colour-vision separation
  as a series colour, so a lighter validated step of the same hue (`#2f4bd4`)
  carries the data.
- One measure across many channels gets **one hue with the extremes picked out** —
  colouring by value double-encodes bar length as colour.
- Scatter plots cap at **two colour classes**; every pair of points sits adjacent,
  and more than three stop being distinguishable under colour-vision deficiency.
- **No dual-axis charts anywhere.** Two y-scales invent a correlation the alignment
  produced rather than the data.
- Status colours are reserved for state and always ship with a word or glyph.
- Confidence intervals are drawn, never implied.

## Pipeline and validation

| Step | Script |
|---|---|
| 1 | `model.py` — clean, reshape, build facts and dims |
| 2 | `build_insights.py` — efficiency, benchmarking, panel model |
| 3 | `alerts.py` — evaluate the rules |
| 4 | `build_site.py` — generate the dashboard |
| 5 | `validate_site.py` — 179 checks on the output |

```bash
python src/run_all.py         # all five
python src/validate_site.py   # broken links, empty charts, NaN leaks, USD leaks
python src/ingest.py          # print the data quality log alone
```

`validate_site.py` also fails the build if a `$` or "USD" reaches a page — in an AED
report that is a factual error, not a formatting slip. There is no separate test
suite; it's this structural check against the built site.

## If the data is refreshed

1. Drop the new extract into `data/raw/` with the same filename.
2. `python src/run_all.py`
3. Regenerate the executive summary — the one deliverable whose numbers are written
   by hand rather than computed.

If the schema changes, `src/ingest.py` is the only module that knows what the raw
file looks like. Everything downstream reads the modelled tables.
